# Development Testing Guide

This guide explains how to test the API adapter and integrate with backend services during development.

## Overview

- **MSW (Mock Service Worker)** intercepts fetch requests and returns mock responses.
- **Unit tests** validate adapter fallback behavior and error handling.
- **Feature flags** allow toggling between local data, mocks, and real backend.

## Quick Start

### Run with Mock API (No Backend Required)

Enable MSW to intercept API calls and return mock data from `src/mocks/handlers.ts`:

```bash
VITE_ENABLE_MSW=true VITE_API_BASE_URL=http://localhost:3001 npm run dev
```

The app will:
1. Start the dev server
2. MSW will intercept all fetch calls to `http://localhost:3001/api/*`
3. Mock handlers in `src/mocks/handlers.ts` will respond with sample data
4. Products page will load with mock products
5. IngredientModal will show mock analysis results

### Run with Local Data Only (Default)

```bash
npm run dev
# VITE_ENABLE_MSW=false (default)
# VITE_USE_REMOTE_API=false (default)
```

The app uses only `src/data/products.ts`, no API calls are made.

### Run with Real Backend

When your backend server is running on `localhost:3001`:

```bash
VITE_ENABLE_MSW=false VITE_API_BASE_URL=http://localhost:3001 VITE_USE_REMOTE_API=true npm run dev
```

The app will:
1. Make real fetch calls to your backend
2. Fall back to local data if requests fail
3. No MSW interception

## MSW Setup

### What MSW Does

- **Service Worker**: Runs in browser and intercepts fetch requests before they hit the network
- **Handlers**: Define how to respond to each API endpoint
- **No network calls**: When using MSW, no actual HTTP requests are made

### File Structure

```
src/mocks/
├── handlers.ts       # Request handlers for each API endpoint
└── browser.ts        # MSW browser setup
public/
└── mockServiceWorker.js  # Service worker (generated by msw init)
```

### Adding a New Handler

To mock a new endpoint, add a handler in `src/mocks/handlers.ts`:

```ts
http.post(`${API_BASE}/api/my-endpoint`, async ({ request }) => {
  const body = await request.json();
  return HttpResponse.json({
    // mock response
    message: "success",
    data: [],
  });
}),
```

Then restart dev server.

## Testing

### Running Unit Tests

```bash
# Install test dependencies (optional, for full test suite)
npm install --save-dev vitest @testing-library/react @testing-library/dom

# Run tests
npm test -- src/services/api.test.ts
```

### What the Tests Validate

- **Fallback behavior**: Adapter returns local data when remote fails
- **Timeout resilience**: 8-second timeout works and falls back gracefully
- **Mock API responses**: Handlers return correct shape and data
- **Error handling**: Network errors are caught and don't break the app

### Test Example: getProductById

```ts
it("should return a product by id from mock API", async () => {
  const product = await api.getProductById("organic-bread");
  expect(product).toBeDefined();
  expect(product?.name).toBe("Organic Whole Grain Bread");
});

it("should use local data when remote API is disabled", async () => {
  const product = await api.getProductById("organic-bread");
  expect(product?.id).toBe("organic-bread");
});
```

## Debugging

### Check if MSW is Running

In browser DevTools Console:

```ts
// Check if service worker is active
navigator.serviceWorker.getRegistrations().then(regs => {
  console.log(regs); // Should show registered service worker
});
```

### Check MSW Logs

MSW logs network interceptions in the browser console. Look for messages like:

```
[MSW] Mocking enabled.
POST http://localhost:3001/api/ingredients/analyze 200 OK
GET http://localhost:3001/api/product/organic-bread 200 OK
```

### Inspect Mock Responses

Open DevTools → Network tab and look for requests. MSW-intercepted requests show as fetch calls with a status code (200, 404, etc.) and the mock response body.

## Scenarios

### Scenario 1: Test Product Listing with Mocks

```bash
VITE_ENABLE_MSW=true VITE_API_BASE_URL=http://localhost:3001 npm run dev
# Navigate to /products
# Products load with mock data from src/mocks/handlers.ts
# No network calls are made
```

### Scenario 2: Test Fallback Behavior

Start dev with mocks enabled, then disable the mock handler (comment out in `handlers.ts`). The adapter will:
1. Attempt remote API call
2. Get network error (no handler)
3. Fall back to local `src/data/products.ts`
4. UI continues to work

### Scenario 3: Real Backend Integration

Backend team implements the API following `openapi.yml` and starts it on `http://localhost:3001`. Then:

```bash
VITE_ENABLE_MSW=false VITE_API_BASE_URL=http://localhost:3001 VITE_USE_REMOTE_API=true npm run dev
```

The app makes real requests to the backend. If backend is down, fallback kicks in automatically.

## Troubleshooting

### MSW Not Intercepting Requests

1. Check `VITE_ENABLE_MSW=true` is set
2. Verify `public/mockServiceWorker.js` exists
3. Check browser console for MSW registration logs
4. Restart dev server

### Mock Responses Not Matching API Contract

Review `src/mocks/handlers.ts` and compare response shape to `openapi.yml`. Ensure:
- Field names match
- Data types are correct
- Required fields are present

### API Calls Still Going to Network

If you see real HTTP requests in Network tab despite `VITE_ENABLE_MSW=true`:
1. Verify service worker registered (`navigator.serviceWorker.getRegistrations()`)
2. Check network requests are going to the correct URL
3. Ensure handler URL pattern matches (`${API_BASE}/api/...`)

## Environment Variables Reference

| Variable | Values | Effect |
|----------|--------|--------|
| `VITE_ENABLE_MSW` | `true` / `false` | Enable Mock Service Worker (dev only) |
| `VITE_USE_REMOTE_API` | `true` / `false` | Enable remote API calls |
| `VITE_API_BASE_URL` | URL string | Base URL for API (required if `VITE_USE_REMOTE_API=true`) |

## Next Steps

1. **Unit tests**: Integrate tests into your CI/CD pipeline (see `.github/workflows/test.yml` if present)
2. **Backend implementation**: Team implements endpoints per `openapi.yml`
3. **Staged rollout**: Enable `VITE_USE_REMOTE_API=true` for a % of users, monitor errors
4. **E2E tests**: Add Cypress/Playwright tests that exercise the full flow with real backend
